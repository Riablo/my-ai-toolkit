# Reflection Checklist

创建、更新或 review skill 时，按这个顺序检查。

## 先看是否真的需要这个 skill

- 这个 skill 提供了哪些任务所需、无法从现有工具和文档直接获得的信息
- 这是不是一句全局规则就能解决的问题
- 是否只是给简单 CLI 加一层包装，直接查工具帮助或 README 就足够
- 这部分知识是不是变化太快，不适合固化进 skill

## 再看 description

- 是否主要在写“何时触发”
- 是否覆盖了真实用户会说的话
- 是否过长
- 是否把执行细节、默认数量、保存路径之类的信息塞进 description
- 是否会和相邻 skill 抢路由

## 再看正文

- 有没有把 help 或 README 复述进去
- 有没有重复已加载的规则或与当前任务无关的通用说明
- 主文件里真正高价值的信息是否足够密集
- 有没有把“默认动作”和“不要自动做什么”讲清楚

## 再看 gotcha

- 最容易误触发或做错的地方有没有写
- 失败时最该补的是不是 gotcha，而不是更长流程
- 有没有写出危险操作、互斥参数、写本机状态、敏感信息处理
- 对照旧版本，必要命令、验收、授权和失败处理是否保留；删减有无等价替代或行为证据

## 再看结构

- 主文件是否过胖
- 条件性重内容是否应该拆去 `references/`
- 重复执行且确定性强的逻辑是否应该拆去 `scripts/`
- 内部引用是否相对 skill 目录，移动内容后入口和章节指向是否同步更新

## 再看维护性

- 这次改动是否影响 README
- 是否检查了本次改变的路由、授权、验证或重试行为，并如实记录未验证项
- 是不是在把 skill 写成一次性文档，而不是可迭代的上下文包
